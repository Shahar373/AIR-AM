# בדיקות עמידות בבית: reboot, ניתוק USB, כיבוי פתאומי

> מסמך ניסוי. סטטוס: **הנוהל והכלי מוכנים, הבדיקות בחומרה טרם בוצעו**.
> מטרה #3 של הפרויקט ("headless ועמיד — עולה באתחול, מתאושש מניתוק USB/קריסה
> לבד, שורד reboot") נבדקה עד היום רק בבדיקות יחידה עם systemd ו-SDR מדומים.
> המסמך הזה הופך אותה לטענה שנמדדה.

---

## 1. מה כבר ידוע מקריאת הקוד, ומה רק החומרה תגיד

**תוקן לפני הבדיקה (v2.25.1), מקריאת קוד ובדיקות שמשחזרות כל אחד מהם:**

1. **כיבוי פתאומי באמצע תו עברי הפיל את התחנה כולה.** הרשומות ב-`acars/vdl2/
   satcom.jsonl` מכילות עברית. חיתוך באמצע תו השאיר UTF-8 לא תקין, ו-
   `_load_*_history` (שרצות ב-`__main__` לפני `app.run()`) זרקו
   `UnicodeDecodeError` — airam-web בלולאת קריסה, בלי מסך ובלי מתזמר.
2. **הרשומה הראשונה אחרי כל כיבוי פתאומי אבדה.** append הודבק לשורה הקטועה.
3. **SDR שלא נמצא באתחול הפיל את ACARS/VDL2/סריקה ל-`off` לצמיתות.** רק קול שמר
   על המצב. גם ניתוק USB באמצע סריקה הפיל אותה ל-`off` אחרי סבב אחד של כשלונות.

**מה רק החומרה יכולה לענות עליו** — ולכן זה עיקר הבדיקה:

| שאלה | למה זה חשוב |
|------|-------------|
| מה עושה כל מפענח (rtl_airband, acarsdec, dumpvdl2, inmarsat-sniffer) כשה-USB נעלם? **יוצא** או **נתקע "active" בשקט**? | יציאה ⇒ systemd מרים אותו מחדש וה-reconcile מכסה. **תקיעה ⇒ אף מנגנון לא ישים לב** (`_live_mode` רואה active). זה הסיכון הלא-ידוע הגדול. |
| אותה שאלה כשה-`sdrplay_apiService` קורס מתחת לצרכן פעיל | `Requires=` מפיץ רק עצירה *מפורשת*, לא קריסה |
| כמה זמן לוקח ל-RSP1B להופיע ב-USB באתחול קר | `BOOT_SDR_WAIT_SEC`=90 הוא הנחה |
| האם כרטיס ה-SD באמת משאיר שורות קטועות/NUL אחרי ניתוק חשמל | התיקונים למעלה מניחים שכן; ייתכן שבפועל זה נדיר |
| מה השעון עושה אחרי אתחול בלי אינטרנט | Pi 5 בלי סוללת RTC מאבד זמן; כל חותמות הזמן נגזרות ממנו |

## 2. הכנה

```bash
cd ~/AIR-AM
git fetch origin claude/vigilant-maxwell-drjt96
git checkout claude/vigilant-maxwell-drjt96     # אחרי המיזוג: git checkout main && git pull
sudo ./install.sh                               # אידמפוטנטי, בונה מחדש רק מה שצריך
```

- **הכלי:** `sudo ~/AIR-AM/scripts/airam-resilience-check` — קריאה בלבד, לא משנה
  כלום. מריצים **לפני** כל תרחיש, **בזמן** (כשרלוונטי), ו**אחרי**, ומדביקים את
  הפלט. הוא מראה: המצב השמור מול מה שרץ, מצב כל שירות + מספר ההפעלות מחדש,
  USB, מה airam-web מדווח (`/api/health`/`scan`/`sdr`), מתח, שעון, שלמות קובצי
  הלוג, ומה המתזמר רשם ביומן מאז האתחול.
- הטלפון עם הממשק פתוח — כדי לראות גם מה המשתמש רואה, לא רק מה השרת אומר.
- אנטנת VHF מחוברת (לא חובה לעמידות, אבל עם תעבורה אמיתית רואים שהפענוח חזר
  ולא רק שהשירות "active").
- ⚠ **SATCOM בבדיקות האלה: רק עם "הזנת LNA חיצונית" מסומן** (`bias_tee=false`).
  חלק מהתרחישים מפעילים את המפענח מחדש בלי פיקוח, ו-bias-T על אנטנת VHF פסיבית
  אינו מה שבודקים כאן.

## 3. התרחישים

זמנים "צפויים" נגזרו מהקוד (‏`RestartSec`=10, שער `airam-wait-sdrplay` עד 30ש',
`MODE_RECONCILE_INTERVAL_SEC`=60) — הם **תחזית**, והמדידה היא מה שקובע.

### R — reboot בכל מצב

לכל מצב: היכנס למצב מהממשק ⇒ check ⇒ `sudo reboot` ⇒ המתן 3 דקות ⇒ check.

| # | מצב לפני | צפוי אחרי |
|---|----------|-----------|
| R1 | 📻 קול | `rtl_airband` active, `app_mode=voice`, שמע בנגן |
| R2 | 📡 ACARS | `airam-acars` active, הודעות בפיד |
| R3 | 🛰️ VDL2 | `airam-vdl2` active |
| R4 | 🔁 סריקה | `api/scan: active`, רגל רצה (או "ממתין" אם אף רגל לא בחלון השעות) |
| R5 | ⏻ off | כל הצרכנים inactive, `app_mode=off`, `api/health ok=True` |
| R6 | 📶 SATCOM | **`off` עם `prev_mode=satcom`** — בכוונה (בטיחות bias-T). ⏻ מציע כניסה ידנית |

### U — ניתוק USB

| # | תרחיש | צפוי |
|---|--------|------|
| U1 | קול/ACARS/VDL2 (כל אחד בנפרד): נתק 10 שניות, חבר | חוזר תוך ~90ש'. **הרץ check גם *בזמן* הניתוק** — ושם את העמודה `Active/Sub` של הצרכן: `activating auto-restart` = המפענח יצא (טוב); `active running` = **נתקע** (ר' §5) |
| U2 | סריקה: נתק 5 דקות, חבר | **חדש:** נשאר `scan` (לא נופל ל-off), `api/health ok=False` בזמן הניתוק, ממשיך לבד אחרי החיבור |
| U3 | **אתחול בלי SDR:** במצב ACARS — נתק, `sudo reboot`, המתן 3 דקות, check, חבר, המתן 2 דקות, check | **חדש:** אחרי האתחול `app_mode=acars` ו-`ok=False` (לא `off`); אחרי החיבור `airam-acars` active. חזור גם עם סריקה |
| U4 | SATCOM (עם הזנה חיצונית): נתק 5 דקות, חבר | **נשאר כבוי** (`Result=start-limit-hit`) — בכוונה, `StartLimitBurst=5`. הממשק מראה תקלה; כניסה ידנית מחדש עובדת |

### S — קריסות תוכנה (בלי לגעת בחומרה)

| # | פקודה | צפוי |
|---|-------|------|
| S1 | `sudo systemctl kill -s KILL airam-web` | עולה תוך ~5ש'; **הצרכן לא מופעל מחדש** (`restarts` שלו לא זז) — `_boot_restore` מזהה שהוא כבר רץ |
| S2 | `sudo systemctl kill -s KILL sdrplay` (בקול, ואז ב-ACARS) | חוזר תוך ~70ש'. כמו ב-U1: בדוק אם הצרכן יצא או נתקע |

### P — חשמל

| # | תרחיש | צפוי |
|---|--------|------|
| P1 | במצב ACARS/VDL2 עם תעבורה (או קול עם הקלטות): **שלוף את החשמל**. חזור 3 פעמים | airam-web עולה; אותו מצב; ב-check: `utf8`/`bad` אולי 1 בשורה האחרונה — **זה בסדר עכשיו**, העיקר שהשירות עלה. `leftovers` ריק (קבצי tmp נוקו) |
| P2 | הפעלה מ-power bank: קול 10 דק', ואז SATCOM (`skip_c` דולק) 10 דק' | `power:` נשאר `0x0`. כל ביט אחר — רשום מתי ובאיזה מצב |
| P3 | אתחול בלי אינטרנט (Wi-Fi כבוי) | רשום את `clock:` ואת השעה שהממשק מציג. ‏`NTPSynchronized=no` + שעה שגויה = ממצא |

## 5. מה ייגזר מהתוצאות

| אם נמצא ש- | אז |
|-------------|-----|
| מפענח **נתקע active** אחרי ניתוק USB או קריסת sdrplay | watchdog לפי *תוצר*, לא לפי מצב השירות: קול — `stats_age` כבר קיים ב-`/api/health`; דאטה — אין הודעה X דקות *וגם* ה-SDR נעלם ב-USB באמצע. **לא בונים לפני שזה נצפה** — watchdog שמפעיל מחדש בגלל שקט בתדר הוא באג בפני עצמו |
| הכול חוזר, אבל לאט מ-90ש' | לקצר `MODE_RECONCILE_INTERVAL_SEC` או את `RestartSec` — לפי מה שנמדד |
| RSP1B מופיע ב-USB אחרי יותר מ-90ש' | להגדיל `BOOT_SDR_WAIT_SEC` (התיקון ב-U3 כבר מונע נפילה ל-off, אבל ההמתנה חוסכת ניסיון כושל) |
| P1 לא משאיר אף שורה פגומה ב-3 ניסיונות | מצוין — התיקונים נשארים כרשת ביטחון זולה |
| P3: שעון שגוי בלי אינטרנט | סוללת RTC ל-Pi 5 (מחבר J5), או חיווי "שעון לא מסונכרן" בממשק |
